# Error model — RFC 9457 problem details

Use `application/problem+json` (RFC 9457, formerly RFC 7807) for every error response. Bespoke error envelopes break interoperability with every HTTP client library and middleware that already speaks problem details. There is no good reason to invent your own.

## The standard schema

This goes in `components.schemas` once and gets `$ref`'d everywhere:

```yaml
Problem:
  type: object
  title: Problem
  description: |
    A problem details object as defined by RFC 9457. Identifies and describes
    a problem that occurred during processing of a request.
  required: [type, title, status]
  properties:
    type:
      type: string
      format: uri
      description: |
        A URI reference identifying the problem type. Should be dereferenceable
        — the URL should serve human-readable documentation about the error.
        Use `about:blank` for problems with no specific type.
      examples:
        - https://errors.example.com/payment-declined
        - about:blank
    title:
      type: string
      description: |
        Short, human-readable summary of the problem. Should be the same for
        all occurrences of the same `type`.
      examples: [Payment declined]
    status:
      type: integer
      minimum: 100
      maximum: 599
      description: HTTP status code generated by the origin server.
      examples: [402]
    detail:
      type: string
      description: |
        Human-readable explanation specific to this occurrence. May include
        instance-specific information; should not include implementation
        details that aid attackers.
    instance:
      type: string
      format: uri-reference
      description: |
        URI reference identifying the specific occurrence — typically the
        request URI or a correlation/trace identifier.
    code:
      type: string
      description: |
        Stable application error code, dot-separated. Stable across versions
        for the same logical error.
      pattern: '^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)*$'
      examples: [payment.declined, validation.required_field]
    errors:
      type: array
      description: |
        Field-level errors when this is a validation failure. Each entry
        identifies a specific field and its problem.
      items:
        type: object
        required: [field, code]
        properties:
          field:
            type: string
            description: JSON pointer or dotted path to the offending field.
            examples: ['/passengers/0/dateOfBirth', 'payment.cvv']
          code:
            type: string
            description: Field-level error code.
            examples: [required, invalid_format, out_of_range]
          message:
            type: string
            description: Human-readable field-level message.
```

## The reusable response

Define the shape once, reference it from every error status code:

```yaml
components:
  responses:
    BadRequest:
      description: The request was malformed or failed validation.
      content:
        application/problem+json:
          schema: { $ref: '#/components/schemas/Problem' }
          examples:
            validation: { $ref: '#/components/examples/ValidationProblem' }
    Unauthorized:
      description: Missing or invalid credentials.
      content:
        application/problem+json:
          schema: { $ref: '#/components/schemas/Problem' }
    Forbidden:
      description: Authenticated but not authorized for this operation.
      content:
        application/problem+json:
          schema: { $ref: '#/components/schemas/Problem' }
    NotFound:
      description: The resource does not exist or is not visible to this caller.
      content:
        application/problem+json:
          schema: { $ref: '#/components/schemas/Problem' }
    Conflict:
      description: |
        State conflict. Common causes: optimistic-lock failure (`If-Match`),
        idempotency-key reuse with a different body, illegal state transition.
      content:
        application/problem+json:
          schema: { $ref: '#/components/schemas/Problem' }
    UnprocessableEntity:
      description: Semantic validation failed; the request was well-formed but invalid.
      content:
        application/problem+json:
          schema: { $ref: '#/components/schemas/Problem' }
    TooManyRequests:
      description: Rate limit exceeded.
      headers:
        Retry-After:
          schema: { type: integer }
          description: Seconds to wait before retrying.
      content:
        application/problem+json:
          schema: { $ref: '#/components/schemas/Problem' }
```

Use them like:

```yaml
paths:
  /bookings/{bookingId}:
    get:
      responses:
        '200': { ... }
        '401': { $ref: '#/components/responses/Unauthorized' }
        '403': { $ref: '#/components/responses/Forbidden' }
        '404': { $ref: '#/components/responses/NotFound' }
```

## Standard problem types

Maintain a per-API table of `type` URIs. Every error code an agent might branch on should have a stable, documented type.

| `type` | Status | When |
|---|---|---|
| `https://errors.example.com/validation` | 400 / 422 | Field validation failed |
| `https://errors.example.com/unauthorized` | 401 | Missing/invalid auth |
| `https://errors.example.com/forbidden` | 403 | No permission |
| `https://errors.example.com/not-found` | 404 | Resource missing |
| `https://errors.example.com/conflict` | 409 | State / lock conflict |
| `https://errors.example.com/precondition-failed` | 412 | `If-Match` mismatch |
| `https://errors.example.com/payment-declined` | 402 | Payment instrument declined |
| `https://errors.example.com/idempotency-key-conflict` | 409 | Same key, different body |
| `https://errors.example.com/rate-limited` | 429 | Quota exceeded |
| `https://errors.example.com/internal` | 500 | Unexpected server error |
| `https://errors.example.com/unavailable` | 503 | Service temporarily down |

The URI does not have to resolve to a live page at the time the spec is written, but it should be planned to. Keep them stable across versions.

## Examples to ship

Define these in `components.examples` and reference from response examples:

```yaml
components:
  examples:
    ValidationProblem:
      summary: Field validation failure
      value:
        type: https://errors.example.com/validation
        title: Validation failed
        status: 422
        detail: One or more fields failed validation.
        instance: /bookings
        code: validation.failed
        errors:
          - field: '/passengers/0/dateOfBirth'
            code: invalid_format
            message: Expected YYYY-MM-DD.
          - field: '/payment/method'
            code: required
            message: Payment method is required.
    PaymentDeclined:
      summary: Card declined
      value:
        type: https://errors.example.com/payment-declined
        title: Payment declined
        status: 402
        detail: Card was declined by the issuer (do_not_honor).
        instance: /bookings/abc123/payments/xyz
        code: payment.declined
    NotFoundProblem:
      summary: Booking not found
      value:
        type: https://errors.example.com/not-found
        title: Resource not found
        status: 404
        detail: No booking with the supplied identifier.
        instance: /bookings/abc123
        code: booking.not_found
```

## What not to put in errors

- Stack traces.
- Database driver messages.
- Internal hostnames.
- Anything that helps an attacker enumerate or escalate.

`detail` is for the developer integrating the API, not for end users. Sanitize.

## Mapping to `x-ai-hints`

Errors agents should branch on get an `x-ai-hints` entry on the operation:

```yaml
x-ai-hints:
  - On 402 with type payment-declined, do not retry without a new payment method.
  - On 409 with type idempotency-key-conflict, the original response was different. Fetch the booking via the original Idempotency-Key flow.
```

This is what tells an agent which retries are safe.
